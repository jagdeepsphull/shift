Shared foundations

Four things built once in Phase 1. This is what a phase with no visible features actually buys.

1 · The e-mail layer

Today: one function, send_email($to, $subject, $message) at app/Helpers/common_helper.php:528. It has no CC, no BCC, no reply-to and no attachment support, and it hard-codes 'protocol' => 'mail' — bare PHP mail(). Every message body is a long HTML string concatenated inside a controller. Nothing is logged: a failure only writes to the error log, and the agency sees no warning.

Target: recipients as a structured list (to/cc/bcc/reply-to), authenticated SMTP, bodies moved into view templates under app/Views/emails/, and an email_log table recording every send with its recipients, subject, status and a re-send handle.

Unlocks: A3, B1, B2, B8, B9, B17, B19, B26 — eight requests that are otherwise eight separate hacks around the same missing parameter.

2 · A sortable shift date

Today: post_job.p_dates is a varchar(200) holding text like 01-08-2026. Nothing can sort or filter on it correctly. The only code that reads it as a date is the expiry cron, which parses it with STR_TO_DATE() each time.

Target: add a real DATE column, backfill it from the existing text, write both columns during a transition period, then move every query and every table sort onto the real column.

Unlocks: A2 and B5 directly; B3, B9, B10 and B21 all depend on being able to ask “which shifts fall in this range”.

3 · An honest status model

Today: a shift carries two columns that disagree. p_approved shows Pending / Live / Rejected / Closed. p_status is an internal flag: the employer sets it to 0 on save, the admin sets it to 1, the public list requires both to be set, and the employer’s Edit and Delete buttons appear only while it is 0. The expiry cron sets p_status = 0, which does not change the visible status and hands the employer their Edit and Delete buttons back on a shift that has already passed.

Target: one column that means “what state is this shift in”, with expiry as a state of its own, and edit permission derived from the state rather than doubling as it.

Unlocks: B7 directly; B14, B15, B18 and B21 all need to ask “can this shift still be changed?” and get a straight answer.

4 · A reusable list toolkit

Today: eleven admin tables share a single DataTables initialisation at app/Views/admin/footer.php:172 that hides column 0 and sorts by it descending. That one block is why the employer list ignores its own SQL ordering, and — on the employer-side Applications table — why the applicant’s name is hidden. There is no multi-select anywhere, and Delete is a row link guarded only by a browser confirm().

Target: per-table configuration instead of one shared block, a checkbox column with a bulk-action bar, and Delete moved inside the edit screen behind a typed confirmation.

Unlocks: B5, B15, B19, B21 and B28.

Open questions

Thirteen questions block 22 of the 31 requests. Each carries our recommendation and the default we will assume if we do not hear back — so silence delays a decision, not the whole build.

Q1 What does “one login for multiple stores” actually mean?

Blocks: B4 B16 B25 B27

Today one row in users is the account, is the licence number, is the address — and a shift copies its province and city straight off that row (app/Controllers/Employer.php:145-146). “Multiple stores” breaks that identity and leaves every existing employer needing a migration.

Options: (a) one login owns many stores under one company and one agreement; (b) each store keeps its own login, grouped under a parent company; (c) a hybrid where a head-office login can act on behalf of any store.

Recommendation: (a). It matches how you described it, keeps one agreement per client, and needs one new store table rather than a rewrite of authentication. Licence number, address and phone move to the store; the person’s name, e-mail and mobile stay on the login.

If we hear nothing: we build (a) and migrate every existing employer into a single store named after their current company, so nothing they see changes on day one.

Q2 What exactly does “Inactive” replace?

Blocks: B7 B15 B21

Three end states already exist — Rejected, Closed, and “expired” (which today is invisible). If all three become “Inactive” you lose the distinction that reporting needs: a shift nobody wanted and a shift that was booked would read the same.

Options: (a) “Inactive” is only the new word for Rejected, and expiry gets its own “Expired” state; (b) “Inactive” is an umbrella covering rejected, expired and closed.

Recommendation: (a). You keep “Booked/Closed” separate for the monthly figures in B10, and the agency can still see at a glance whether a shift died because it was rejected or because the date passed.

If we hear nothing: (a). Also assumed: an inactive shift is hidden from the public site but still visible to the agency and to the employer who posted it, and editing its date does not automatically revive it.

Q3 What kind of “live chat” is acceptable on this hosting?

Blocks: B11

The site runs on shared hosting: no WebSockets, no background worker, no queue. “Live” here can only mean the browser asking the server every few seconds, or a third-party widget embedded in the page.

Options: (a) in-house message centre with 5-second polling — messages stay in your database, you own the history; (b) a hosted widget (Tawk.to, Crisp) — genuinely live, but conversations live on someone else’s servers, which matters for pharmacist and pharmacy data; (c) message centre with no live element at all, i.e. an inbox with e-mail notification.

Recommendation: (c) first, then (a) if you find you need immediacy. Most of what you described — telling an applicant a shift changed, asking an employer a question — is asynchronous. An inbox with e-mail notification delivers 90% of the value for a third of the cost.

If we hear nothing: this stays in Phase 6, unpriced. We will not start it on an assumption.

Q4 Whose phone number becomes visible to whom, and when?

Blocks: B24 B25

Right now no phone number and no e-mail address is shown in either direction. A booked applicant sees only the store name, store number and address (app/Views/applicant/applied_jobs.php:43-46); the employer sees only the applicant’s name, licence and province. Your request opens that up in one direction only.

Options: (a) store phone visible to the booked applicant only, from booking until the shift ends; (b) visible to anyone who applied; (c) visible on the public shift listing.

Recommendation: (a), and the employer’s personal mobile stays hidden from everyone but the agency — which is exactly why the store needs its own phone number rather than reusing u_phone.

If we hear nothing: (a), and the applicant’s own number is not exposed to the employer in return — the agency stays the go-between.

Q5 CC or BCC for the agency copy?

Blocks: A3 B8

A CC shows every recipient’s address to every other recipient. On a booking e-mail that means the applicant sees the employer’s address and vice versa — the exact thing Q4 says you want to avoid.

Recommendation: BCC team@pickashift.ca on the existing two separate e-mails. You get your copy, nobody’s address leaks, and the applicant and employer keep receiving the tailored message each already gets (they contain different hourly rates — see B2).

If we hear nothing: BCC, two separate e-mails, exactly as today.

Q6 May we move e-mail onto a real sending service?

Blocks: B1 — and the delivery of every other e-mail in the system

“Not working” has two possible meanings and the fix is different for each. The code sends through PHP mail() from pickashift@pickashift.ca. If the domain has no SPF and DKIM records, mail from it is filtered as spam regardless of what the code does — so no code change alone can guarantee delivery.

Needed: permission to switch to authenticated SMTP (SendGrid, Mailgun, Microsoft 365 — any is fine) and to add two DNS records to pickashift.ca.

Recommendation: yes, and do it in Phase 1. Everything in Phase 2 is worthless if the mail lands in junk. We can prove the difference with a before/after delivery test to Gmail and Outlook.

If we hear nothing: we build the layer so the provider is a one-line setting, ship it pointed at the current server, and hand you the DNS records to apply when you are ready.

Q7 Can one shift ever cover more than one date?

Blocks: A2 B9

p_dates is 200 characters wide and the applicant-side date picker still has multi-date selection switched on — a leftover from an earlier design. Every current row holds a single date, but the field could hold several, and “sort by date” and “remind one day before” both need to know which date they mean.

Recommendation: one date per shift. If a pharmacy needs Monday and Wednesday, that is two shifts — which also lets an applicant take one and not the other, and makes B20 (duplicate a shift) the natural way to create them.

If we hear nothing: one date per shift; the reminder in B9 sends at 09:00 America/Toronto on the day before.

Q8 What happens to the person being replaced, and to the rate?

Blocks: B14 B18

The rate lives on the shift, not on the booking, so “the rate of the new person may vary” has nowhere to be stored. And the original applicant has already had a confirmation e-mail naming a date, a store and a rate.

To decide: does the replaced applicant get a cancellation notice? Is the new rate visible to the employer, or only to the agency? Does the shift keep advertising its original rate?

Recommendation: move the agreed rate onto the booking record, keep the shift’s advertised rate untouched, and always send the replaced applicant a short cancellation e-mail — silence there is how you lose a pharmacist.

If we hear nothing: as recommended, with the employer seeing only their own rate (the one they agreed to pay), which is already how the two booking e-mails differ today.

Q9 Must the database backup really go out by e-mail?

Blocks: B22

That file contains every pharmacist’s and pharmacy’s personal data. E-mail is unencrypted in transit between servers, lands in a mailbox that may be shared, and is retained indefinitely. Shared hosting may also block mysqldump outright.

Options: (a) an expiring download link inside the admin panel; (b) a scheduled encrypted copy pushed off-site (Google Drive, S3, Dropbox); (c) e-mail as asked, with the archive password-protected.

Recommendation: (a) for on-demand and (b) for scheduled. Both give you the backup without a copy of your entire client base sitting in an inbox.

If we hear nothing: deferred. We will not ship an unencrypted PII export by e-mail on an assumption.

Q10 Who may be mass-e-mailed, and how do they opt out?

Blocks: B19 B26

Canada’s anti-spam law treats a bulk message to your user base as commercial electronic messaging: it needs a basis for consent, a sender identification block and a working unsubscribe. A privacy policy update sent to everyone is exactly that.

To decide: is the policy notice a one-off to all active users, or shown to people as they next log in? Do you hold consent records? Who signs off a bulk send?

Recommendation: treat the policy update as transactional — send it once to active users, with your postal address and an unsubscribe link in the footer, and also show an in-app banner on next login for anyone who did not open it. Add an unsubscribe flag to the user record now, while it is cheap.

If we hear nothing: we build the unsubscribe flag and the footer, and leave the actual send behind a confirmation step that names the recipient count.

Q11 “E-mail directly from the e-mail link” — your mail client, or ours?

Blocks: B19

Two very different things. A mailto: link opens Outlook and the system never knows what was said. An in-app composer keeps the message, the template and the history in the send log that B8 gives you.

Recommendation: in-app composer for anything the agency does as the agency, and a mailto: as a secondary “open in my mail app” action for one-off personal notes. You get the audit trail without losing the quick option.

If we hear nothing: both, as described.

Q12 What does “new” mean, and should a delete erase history?

Blocks: B3 B10

The “new items” tab and the monthly report both need reliable creation timestamps. Sign-ups through the public form never set created at all (app/Controllers/Front.php:436-457), so “new applicants this month” cannot be answered today for anyone who registered themselves. Separately, B21’s manual delete would erase the rows B10 counts.

To decide: is “new” since you last looked, or a fixed window such as 7 days? Should deleting a closed shift remove it from the monthly booking figures?

Recommendation: “new” = since your last visit to the tab, with a 7-day fallback for a first visit. And make deletes soft — the row disappears from the list but the monthly figures stay stable, which is the whole point of having them.

If we hear nothing: as recommended. We will also backfill created for existing rows where it can be inferred, and flag the ones where it cannot.

Q13 What should Delete actually do?

Blocks: B21 B28

Moving Delete inside Edit changes the pattern on eleven lists. More importantly, it is not clear what a delete should mean: deleting an employer today leaves their shifts and every application against those shifts pointing at a row that no longer exists.

To decide: does Delete disappear from the list rows entirely? Should deleting an employer or a shift that has historic bookings be blocked, soft-deleted, or allowed to cascade?

Recommendation: Delete moves inside Edit and requires typing the record’s name to confirm. Anything with historic bookings is soft-deleted, never removed — you keep the audit trail and the monthly figures, and nothing is ever destroyed by a mis-click.

If we hear nothing: as recommended. The existing “you cannot delete this, it is in use” guards stay in place underneath.
