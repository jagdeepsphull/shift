What changed

The tick box already existed on the four user forms — applicant add/edit and employer add/edit — and wrote users.u_agreement_done. Until now that was the only place the answer could be seen: to find out who had signed, somebody had to open records one at a time. This puts the same answer on the lists, so the accounts still to chase can be spotted, sorted and searched from one screen.

Where the answer comes from

users.u_agreement_done — TINYINT(1) NOT NULL DEFAULT 0, added by the migration 2026-08-20-090000_AddUserAgreementDone that this release already carries. It is a back-office fact: nothing on the public site writes it, and no account holder can set it.

A store has no agreement of its own. A location is not a signatory — the employer who holds it is. So the store list reports the owning account’s answer, and every branch of one chain shows the same word.

Decisions worth knowing

Four small choices that are not obvious from the diff, and the reason each one went the way it did.

1 · “Yes” and “No”, not a tick

Every admin list carries Excel, PDF and print buttons, and the exporter takes the text of a cell. A tick icon exports as an empty column. Spelling the answer out is the same reason the Status column says Active rather than showing a green dot — and it gives the search box and the column sort something to work with.

2 · Before Status, not after it

The shared table script hands responsive priority to the last two columns, on the standing assumption that every admin list ends Status → Action. A column slipped between them would have taken Status off the screen on a narrow window. Putting it ahead of Status also leaves every screen’s default sort column at the index it already used.

3 · One wording on all four

The cell is rendered by a single helper, agreementDoneBadge(), rather than hand-written into four views. The office reads down these lists looking for the same thing on each; four wordings would make that four separate readings, and a later change of mind would mean four edits.

4 · Status is not asked about

userAgreementDone() looks the owner up without requiring an approved account — deliberately unlike getPharmacyName(), which does. A pending employer who has already signed should say so, because that pair is usually exactly what the office is hunting for.

No extra queries per row. The store list asks the owner’s answer through lookupRow(), the request-scoped cache the province, city and employer name helpers already use — so a page of thirty branches of one chain asks the database once, not thirty times.

How the new tests read the cell

By the badge’s own words, not by column number: the four listings put it at different positions, and the responsive plugin moves cells about besides. Nothing else in these rows says just Yes or No — Status spells Active and Pending, the store Links say Map pin and Website. Each assertion reads the stored value first, so the tests hold whichever way the earlier tests in the file left the fixture.

One unrelated failure. admin-stores.spec.js › “the store list is reachable from the sidebar and shows every store” fails — but it fails identically with this change stashed, so it is pre-existing and not caused here. It looks like paging: the fixture store is not on the first page of the unscoped list. Left alone as out of scope.

Deploying

Nothing new to run. The column these screens read was already part of the 2026-08-20 release.

  1. Upload the five changed PHP files listed above.
  2. Make sure users.u_agreement_done exists — migration 2026-08-20-090000_AddUserAgreementDone, or section 9 of deploy/release-2026-08-20.sql, which is written to be safe to re-run.
  3. Without that column the four forms already fail on save, so in practice it is applied before these listings are ever seen. The views fall back to No rather than erroring if it is somehow missing.
